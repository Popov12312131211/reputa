# AUTH-010 — Backend: регистрация сотрудников с идентификатором

## Статус
Выполнено.

## Описание
Отдельный эндпоинт регистрации сотрудников `POST /auth/register/employee`: те же поля, что при обычной регистрации (AUTH-001), плюс обязательное поле "Идентификатор" и роль `employee`.

Формат идентификатора: одна английская буква + 3 произвольные цифры + literal "room19" (например "A123room19"). Валидация формата — на бэкенде.

## Принятое решение
**Достаточно проверки формата.** Для MVP список/база допустимых идентификаторов не вводится — регистрация допускает любой идентификатор, прошедший проверку формата (регэксп `^[A-Za-z][0-9]{3}room19$`). Проверка принадлежности к команде по списку/базе выносится в бэклог, если понадобится ужесточить контроль. Решение принято по аналогии с остальным MVP (регистрация/вход без подтверждения номера/телеграма — см. AUTH-001/AUTH-004).

## Затронутые файлы
- `backend/app/core/constants.py` — `EMPLOYEE_IDENTIFIER_PATTERN`.
- `backend/app/schemas/auth.py` — `RegisterRequestBase` (общие поля/валидация для обеих регистраций), `RegisterRequest`, `EmployeeRegisterRequest` (поле `identifier` с валидацией формата).
- `backend/app/routers/auth.py` — общий хелпер `_create_user`; эндпоинт `/register/employee` (роль employee всегда, независимо от bootstrap-правила).
- `backend/tests/test_auth.py` — `TestEmployeeRegisterEndpoint` (успех/роль/формат/пустой идентификатор/дуп дублированный логин/гонка).
- `backend/tests/test_auth_me_e2e.py` — сквозной сценарий «регистрация сотрудника → вход → /auth/me» и отсев неверного формата.

## Проверка
- `python -m pytest` в `backend/` — 211 passed (9 новых тестов по AUTH-010).
- `POST /auth/register/employee` с валидным идентификатором → 201, роль `employee`.
- Идентификатор `"badroom19"`, `"A12room19"`, `"A1234room19"` и т.п. → 422, пользователь не создаётся.
- Дублирующийся логин → 409 (включая гонку, IntegrityError).
- Фронтенд `RegistrationWork.jsx` уже постит на `/auth/register/employee` (AUTH-011) — эндпоинт теперь существует; после успешной регистрации форма уводит на `/loginWork`.

## Что осталось
- Сквозная проверка фронтенда `/registrationWork` после AUTH-010 — это AUTH-011.
- При необходимости — проверка идентификатора по списку/базе команды (вынесено в бэклог).
