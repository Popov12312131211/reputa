# RULES.md

## Git

- Не коммитить самостоятельно.
- Не делать `git push` без явного разрешения пользователя.
- Не менять историю Git (rebase, reset --hard, force-push) без явного разрешения.
- Не удалять ветки, теги или remote без подтверждения.

## Код

- Следовать существующему стилю и архитектуре проекта (React на фронтенде, FastAPI + PostgreSQL на бэкенде).
- Перед добавлением новой абстракции сначала проверить, нет ли уже подходящего решения в проекте.
- Не дублировать существующую логику.
- Предпочитать простые решения сложным абстракциям — MVP делается в сжатый срок.
- Не добавлять зависимости без необходимости.
- Не использовать устаревший API, если есть поддерживаемая альтернатива.
- Сложный или неочевидный код должен сопровождаться комментариями, объясняющими "почему", а не просто "что делает код".
- Не оставлять TODO, FIXME и временные обходные решения без объяснения или ссылки на задачу.
- Не оставлять отладочный код, `console.log`, `print`, временные файлы или закомментированный старый код.
- Весь текст интерфейса в новых компонентах должен идти через ключи i18n (namespace i18next). Хардкод строк запрещён.
- Все магические числа и конфигурационные константы (время жизни токена, длина пароля, лимиты пагинации, ограничения длины полей и т.п.) выносятся в отдельный файл констант (например, `constants.py` для бэкенда) и не хранятся внутри бизнес-логики или схем.

## Интеграция и уже реализованный функционал

- Отдельного API_CONTRACT в проекте нет.
- Перед реализацией новой функциональности агент обязан сначала поискать в проекте уже реализованный эквивалент (эндпоинт, компонент, функцию) — по коду, а не по документации контракта.
- Если существующая реализация найдена — переиспользовать её вместо создания новой.
- Если не найдена — реализовать заглушку (mock/stub), которая не блокирует остальной сценарий, и явно отметить в TASKS.md необходимость довести до реальной реализации.

## Тесты

- При добавлении новой функции/метода обязательно добавлять тесты.
- При исправлении бага обязательно добавлять регрессионный тест, воспроизводящий баг.
- Перед завершением задачи запускать существующий набор тестов.
- Не удалять и не ослаблять тесты только для того, чтобы они проходили.
- Не менять ожидаемые значения в тестах без понимания причины изменения.
- Тесты должны проверять поведение, а не конкретную внутреннюю реализацию.
- Для критичной бизнес-логики (расчёт скоринга, пороговая автообработка заявок) стремиться к покрытию граничных случаев.
- Не использовать реальные внешние сервисы в unit-тестах (включая реальные вызовы Telegram Bot API и ML-моделей) — использовать моки/стабы/фейки.
- Новые интеграционные тесты явно отделять от unit-тестов.

## Документация

- README.md писать на русском языке.
- Документация должна соответствовать текущему состоянию кода.
- При изменении публичного API обновлять соответствующую документацию.
- Примеры кода в документации должны быть рабочими и актуальными.
- Breaking changes должны быть отражены в документации.
- Не дублировать одну и ту же информацию в нескольких местах без необходимости.
- Не менять спецификации (PRODUCT.md, PLAN.md) без согласования с пользователем.

## Работа с TASKS.md и openspec/tasks/

- Агент имеет право самостоятельно редактировать TASKS.md — статусы задач, владелец, прогресс, блокер, текущий файл выполнения, следующий шаг.
- Для каждого выполнения обязательно вести краткую запись в `openspec/tasks/{id}.md`, где `{id}` — ID задачи из TASKS.md (например `openspec/tasks/APP-001.md`): что сделано, какие файлы затронуты, что осталось сделать, есть ли блокеры и что передаётся дальше. **Имя файла — это ID задачи, а не дата или timestamp.**
- Запись в `openspec/tasks/{id}.md` должна быть краткой (по сути, а не журналом) — без полного лога терминала, diff'ов и истории переписки.
- Не указывать субъективный процент готовности ("готово примерно на 80%") — вместо этого явный статус и конкретный следующий шаг.

## Безопасность

- Никогда не хранить секреты в репозитории.
- Не выводить учётные данные, токены и чувствительные данные в логи.
- Не отключать проверку TLS/SSL-сертификатов без веской причины.
- Валидировать данные, приходящие от пользователя или внешних систем (включая содержимое загружаемой банковской выписки и данные из Telegram-канала).
- Не выполнять shell-команды с непроверенным пользовательским вводом.
- Не использовать `eval` и подобные механизмы без крайней необходимости.
- Перед добавлением зависимости проверять её происхождение и поддержку.

## Прочее

- Не изменять код, не относящийся к текущей задаче. Если найдена отдельная проблема — сообщить о ней отдельно, не исправляя попутно.
- Перед изменением существующей архитектуры сначала изучить связанные файлы и зависимости.
- Перед внесением изменений сверяться с актуальными PRODUCT.md и PLAN.md и следить, чтобы реализация им соответствовала.
- Перед написанием кода искать существующие похожие реализации в проекте.
- Если требования неоднозначны и решение может существенно повлиять на архитектуру — сначала задать вопрос.
- Если задача понятна — не задавать лишних вопросов и сразу выполнять её.
- После изменений отчитываться:
    1. что изменено
    2. какие тесты запускались
    3. результаты тестов
    4. какие проблемы остаются
- Не утверждать, что тесты/линтеры/сборка прошли, если они фактически не запускались.
- Не утверждать, что проблема исправлена, если это не проверено.
