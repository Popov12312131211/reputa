# PLAN.md

## Технический стек

**Фронтенд:** React

**Бэкенд:** Python (FastAPI)

**БД:** PostgreSQL

**Скоринг:** ML-модель — локальная или бесплатная модель по API (выбор конкретной модели — по ходу реализации)

**Авторизация:** JWT в httpOnly cookie, без refresh-токена (TTL — сутки). Без Redis и серверных сессий — избыточно для срока хакатона.

**Обработка банковской выписки:** парсинг в структурированные данные сразу при загрузке, исходный файл не хранится

**Интеграция с Telegram:** Telegram Bot API (парсинг публичного канала пользователя, реализация — при наличии времени)

**Деплой на демо:** локально с ноутбука, без внешнего хостинга

## Архитектурные решения

- Аутентификация не хранит состояние на сервере (JWT), что упрощает деплой с ноутбука без дополнительной инфраструктуры
- Выписка не хранится как файл — сразу на этапе загрузки приводится к структурированным данным, которые и используются скорингом; это снимает вопрос безопасного хранения банковских документов на MVP
- Скоринг по выписке (детерминированная часть: остаток, регулярность, доля трат) и скоринг по Telegram (ML/LLM-часть) — независимые модули, объединяемые в итоговую оценку. Это позволяет запустить систему на День 1 без Telegram-части и добавить её на День 2, не переписывая ядро
- Пороговая автоматизация (авто-одобрение/авто-отказ) реализуется как отдельный слой поверх итоговой оценки, настройки порогов хранятся в БД и редактируются в `/employee/settings` — не захардкожены в коде

## Этапы

### Этап 1. Инфраструктура и модель данных

Реализация: развернуть React-фронтенд и FastAPI-бэкенд, поднять Postgres, определить базовые схемы (User, Application, ScoreResult).
Затрагивает: backend/models, backend/db, frontend (базовый каркас проекта).
Проверка: health-check эндпоинт отвечает, миграции применяются без ошибок.
Критерий: проект поднимается локально одной командой, бэкенд читает и пишет в БД.
Зависит от: нет.

### Этап 2. Аутентификация

Реализация: регистрация и вход заёмщика, вход для сотрудников по коду (дефолт "123456"), выдача JWT в httpOnly cookie.
Затрагивает: backend/auth, backend/models (User), frontend (login, registration, loginWork).
Проверка: сквозной сценарий регистрация → вход → доступ к защищённому эндпоинту; запрос без валидного cookie отклоняется.
Критерий: неавторизованный доступ к приватным страницам невозможен, авторизованный проходит без ошибок.
Зависит от: Этап 1.

### Этап 3. Заявка и скоринг по выписке

Реализация: форма подачи заявки (`/user/new`), парсинг банковской выписки в структурированные данные при загрузке, расчёт оценки на основе выписки, пороговая автообработка (авто-одобрение/авто-отказ по настройкам).
Затрагивает: backend/scoring (модуль выписки), backend/models (Application), frontend (user/new, user/my, user/my?menu={id}).
Проверка: подача заявки с тестовой выпиской возвращает согласованную оценку 0–100; заявка корректно распределяется по порогам из настроек.
Критерий: заявка проходит полный путь от создания до авто-решения либо до попадания в очередь сотрудника.
Зависит от: Этап 2.

### Этап 4. Кабинет сотрудника

Реализация: очередь актуальных заявок и список всех заявок, карточка заявки с решением (одобрить/отклонить), настройка порогов автоматизации.
Затрагивает: backend/employee, frontend (employee/settings, employee/newApplication, employee/application).
Проверка: сотрудник видит заявки в правильных списках; решение сохраняется и отражается в кабинете заёмщика.
Критерий: ручное решение сотрудника меняет статус заявки и видно заёмщику без дополнительных действий.
Зависит от: Этап 3.

### Этап 5. Telegram-скоринг (расширение)

Реализация: парсинг публичного Telegram-канала через Telegram Bot API, интеграция сигнала в итоговую оценку поверх уже работающего скоринга по выписке.
Затрагивает: backend/scoring (модуль telegram), backend/models (Application — поле telegram-сигнала).
Проверка: для канала с явно позитивным и явно негативным содержанием сигнал предсказуемо сдвигает итоговую оценку в соответствующую сторону.
Критерий: наличие или отсутствие telegram-сигнала не ломает сценарий, отработанный на Этапах 3–4.
Риск: публичный API может не отдать историю сообщений без нужных прав доступа или для закрытых каналов.
Откат: при недоступности канала — использовать только оценку по выписке, как на Этапе 3, без блокировки основного сценария.
Зависит от: Этап 3.
