## Этап 1. Инфраструктура и модель данных

- [x] **INFRA-001** — Бэкенд-скелет (FastAPI + Postgres)

  Поднять FastAPI-приложение с базовой структурой (`app/main.py`, `app/core`, `app/db`), настроить подключение к PostgreSQL через SQLAlchemy, добавить эндпоинт `/health`, возвращающий статус подключения к БД. Все параметры подключения — через переменные окружения.

- [x] **INFRA-002** — Фронтенд-скелет (React)

  Поднять базовый React-проект с роутингом, завести пустые страницы-заглушки под все известные маршруты: `/`, `/login`, `/registration`, `/loginWork`, `/user/settings`, `/user/my`, `/user/my?menu={id}`, `/user/new`, `/employee/settings`, `/employee/newApplication`, `/employee/application`, `/employee/application?menu={id}`. Подключить заготовку i18next с пустым namespace.

  > На этом этапе страницы — просто заголовок с названием маршрута, без вёрстки и логики.

- [x] **INFRA-003** — Модель User + миграция

  Таблица пользователей: ФИО, дата рождения, логин, пароль (хеш), номер телефона, телеграм, роль (пользователь/сотрудник). Миграция через Alembic.

- [x] **INFRA-004** — Модель Application + миграция

  Таблица заявок: id, ссылка на пользователя, сумма, цель/причина кредита, телеграм, телеграм-канал, статус (в очереди / авто-одобрено / авто-отказано / одобрено сотрудником / отклонено сотрудником), итоговая оценка.

  > Формат ID заявки: случайная строка из 10 символов (не автоинкремент — например, хеш от даты/времени запроса на бэкенде). Сейчас в модели ID — числовой автоинкремент; при реализации реального backend-эндпоинта списка заявок (APP-002+) ID должен генерироваться указанным способом, а не через autoincrement.

- [x] **INFRA-005** — Модель ScoreResult + миграция

  Таблица результатов скоринга по заявке: список позитивных сигналов, список факторов риска, психологический портрет заёмщика (три метрики по шкале 0–10: стабильность работы, финансовая грамотность, ответственность), отчёт для кредитного комитета (содержимое + дата последнего обновления), итоговая оценка (0–100).

  > Психологический портрет и отчёт для комитета формируются на основе telegram-анализа (TG-002) — до Этапа 5 заполняются захардкоженными значениями.

- [x] **COMP-001** — Общий компонент меню/сайдбара (frontend)

  Переиспользуемый компонент навигации для кабинета пользователя и кабинета сотрудника: "Настройки", "Мои заявки" / "Актуальные заявки" + "Все заявки", "Создать заявку" — пункты отличаются по роли.

- [ ] **INFRA-006** — CORS (backlog)

  CORSMiddleware сейчас на бэкенде отсутствует — на локальной разработке это не проблема (frontend ходит на backend same-origin через прокси nginx/vite). Настроить `CORSMiddleware` на бэкенде перед любым деплоем, где frontend и backend не находятся на одном origin (без прокси).

## Этап 2. Аутентификация

- [x] **AUTH-001** — Регистрация (backend)

  Эндпоинт регистрации: принимает ФИО, дату рождения, логин, пароль, номер телефона, телеграм. Валидация пароля (8–64 символа, латинские строчные и заглавные буквы, цифры, спецсимволы) и формата остальных полей — без подтверждения номера и телеграма.

- [x] **AUTH-002** — Вход пользователя (backend)

  Эндпоинт входа по логину/паролю, выдача JWT в httpOnly cookie без refresh-токена (TTL — сутки).

- [x] **AUTH-003** — Вход для сотрудников (backend)

  Отдельный эндпоинт входа по коду с телефона (дефолтный код "123456"). Если в БД нет ни одного пользователя — первый зарегистрированный автоматически становится сотрудником.

- [x] **AUTH-004** — Страница регистрации (frontend `/registration/`)

  Поля: ФИО, дата рождения, логин, пароль (с подсказкой требований к сложности), повторите пароль, номер телефона, телеграм. Отправка на AUTH-001 (`POST /auth/register`), после успеха — переход на `/login`.

  > Без подтверждения номера и телеграма — только валидация формата, осознанное решение для MVP.

- [x] **AUTH-005** — Страница входа (frontend `/login/`)

  Поля: логин, пароль. Ссылки "Забыли пароль?" и "Нет аккаунта? Регистрация". Отправка на AUTH-002 (`POST /auth/login`), после успеха — в кабинет по роли.

- [x] **AUTH-006** — Страница входа для сотрудников (frontend `/loginWork/`)

  Поля: логин, код с телефона, пароль. Ссылки "Отправить код" и "Забыли пароль?". Отправка на AUTH-003 (`POST /auth/login/employee`), после успеха — в кабинет сотрудника.

- [x] **AUTH-007** — Защита приватных маршрутов

  Middleware на бэкенде (проверка JWT из cookie) и route guard на фронтенде: неавторизованный не должен попадать на `/user/*` и `/employee/*`.

## Этап 3. Заявка и скоринг по выписке

- [x] **APP-001** — Форма новой заявки (frontend `/user/new`)
  Поля: сумма (валидация: от 1 000 до 10 000 000, ошибка "Укажите сумму больше нуля" при пустом/некорректном значении), цель/причина кредита (свободный текст, textarea), телеграм (@username), актуальный телеграм-канал (@channel — обязательное поле, без него форма не отправляется), выписка из банка (загрузка файла), чекбокс согласия с политикой конфиденциальности. В одной строке с кнопкой "Запросить" — поле пароля (доп. верификация личности перед отправкой заявки). Кнопка "Запросить".
  Плейсхолдер поля "Причина" — один из 5 заранее заданных забавных вариантов, выбирается случайно при каждой загрузке страницы (не статичный текст).

- [x] **APP-002** — Эндпоинт создания заявки (backend)

  Приём данных формы и файла выписки, создание записи Application со статусом "в обработке".

  > Статус при создании — `in_queue` («в очереди»): отдельного статуса «в обработке» в схеме нет (INFRA-004). Файл выписки принимается и отбрасывается (не сохраняется), парсинг — в STMT-001. Авторизация — JWT из httpOnly cookie (зависимость `get_current_user`, выдача токена — AUTH-002).
  > Фронтенд APP-001 опирается на заглушку (`serverNotReady` в `UserNew.jsx`) до реализации этого эндпоинта.

- [x] **STMT-001** — Парсинг банковской выписки

  При загрузке файл сразу парсится в структурированные данные (остаток, поступления, траты по категориям за 3 месяца). Сам файл не сохраняется — хранятся только структурированные данные. Реализовано в `app/scoring/stmt_parser.py` (Альфа-Банк, СберБанк, Озон Банк), подключено в `POST /applications` как валидация загружаемой выписки; фикстуры и тесты — `tests/test_statement_parser.py`, `tests/fixtures/`.

- [ ] **STMT-002** — Расчёт скоринга по выписке

  Расчёт вклада в итоговую оценку на основе среднего остатка, регулярности поступлений, доли трат на необходимые товары. Формирует часть позитивных сигналов / факторов риска в ScoreResult.

- [x] **APP-003** — Пороговая автообработка заявки

  После расчёта итоговой оценки сравнение с порогами из настроек сотрудника (EMP-002): если оценка ≤ порога авто-отклонения — статус "авто-отказано"; если оценка ≥ порога авто-одобрения — статус "авто-одобрено"; иначе заявка уходит в очередь сотрудника.

- [ ] **APP-004** — Список заявок пользователя (frontend `/user/my`)

  Таблица заявок пользователя: id, статус, сумма, итоговая оценка.

  > Бэкенд-эндпоинт заявок пользователя ещё не реализован (APP-002+). Фронтенд APP-004 опирается на мок-заглушку (`MOCK_APPLICATIONS` в `UserMy.jsx`) с попыткой запроса `GET /api/user/applications`; после реализации эндпоинта останется подключить его вместо мока.

- [ ] **APP-005** — Детальная карточка заявки пользователя (frontend `/user/my?menu={id}`)

  Отображение: id заявки, запрошенная сумма, цель кредита. Блок "Рекомендации системы" — позитивные сигналы и факторы риска двумя списками. Блок "Психологический портрет заёмщика" — три метрики по шкале 0–10 (стабильность работы, финансовая грамотность, ответственность). Блок "Отчёт для кредитного комитета" — кнопка скачивания + дата последнего обновления. Итоговая оценка — спидометр "Благонадёжность (0–100)".

- [ ] **APP-006** — Настройки профиля пользователя (frontend `/user/settings` + backend)

  Редактируемые поля: ФИО, логин, телеграм, номер телефона, пароль (со сменой).
  

## Этап 4. Кабинет сотрудника

- [ ] **EMP-001** — Настройки профиля сотрудника (frontend `/employee/settings` + backend)

  Аналогично APP-006: ФИО, логин, телеграм, номер телефона, пароль.

- [x] **EMP-002** — Настройка порогов автоматизации

  Часть `/employee/settings`, блок "Автоматизация": порог "авто-отклонение ≤ X" и порог "авто-одобрение ≥ Y". Backend хранит оба порога в БД (не хардкод), их использует APP-003.

- [ ] **EMP-003** — Список актуальных заявок (frontend `/employee/newApplication`)

  Таблица заявок, ожидающих решения сотрудника (не попавших под автообработку): id, статус, ФИО заёмщика, сумма, итоговая оценка.

- [ ] **EMP-004** — Список всех заявок (frontend `/employee/application`)

  Таблица всех заявок вне зависимости от статуса: id, статус, ФИО, сумма, итоговая оценка.

- [ ] **EMP-005** — Детальная карточка заявки сотрудника (frontend `/employee/application?menu={id}`)

  Тот же разбор, что и в APP-005 (рекомендации системы, психологический портрет, отчёт, спидометр), плюс кнопки "Одобрить" и "Отклонить".

- [ ] **EMP-006** — Эндпоинт решения по заявке (backend)

  Приём решения сотрудника (одобрить/отклонить), обновление статуса заявки — изменение сразу отражается в `/user/my` у заёмщика.

## Этап 5. Telegram-скоринг

- [ ] **TG-001** — Парсинг данных Telegram (канал + публичные чаты)

  Получение сообщений из двух типов источников через Telegram Bot API: публичный канал пользователя по адресу, указанному в заявке, и открытые групповые чаты, где пользователь состоит и/или пишет.

  > Если канал или чат недоступен или закрыт — просто не учитывается в оценке, без отдельной обработки ошибки для пользователя.

- [ ] **TG-002** — Расчёт скоринга и психологического портрета по объединённым данным канала и чатов

  На старте — захардкоженный сценарий (заранее заданные позитивные сигналы, факторы риска, метрики портрета и текст отчёта для демо). Если будет время — реальный анализ лексики, частоты упоминаний работы, подписок на финансовые каналы (LLM+NER).

- [ ] **TG-003** — Интеграция telegram-сигнала в итоговую оценку

  Объединение сигнала из TG-002 с оценкой по выписке (STMT-002) в единый итоговый балл. Должно работать и в отсутствие telegram-сигнала (см. TG-001) — тогда используется только оценка по выписке.
