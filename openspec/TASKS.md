- [ ] **INFRA-005** — Модель ScoreResult + миграция

  > Психологический портрет и отчёт для комитета формируются на основе telegram-анализа (TG-002) — до Этапа 5 заполняются захардкоженными значениями.

- [ ] **COMP-001** — Общий компонент меню/сайдбара (frontend)

  Переиспользуемый компонент навигации для кабинета пользователя и кабинета сотрудника: "Настройки", "Мои заявки" / "Актуальные заявки" + "Все заявки", "Создать заявку" — пункты отличаются по роли.

- [x] **COMP-002** — Компонент диаграммы "Благонадёжность" (ScoreGauge, frontend)

  Переиспользуемый спидометр «Благонадёжность (0–100)», один пропс — числовое значение 0–100. Позиция красного маркера, длина синей заливки и цвет числа/точки вычисляются внутри компонента из значения. Структура сверху вниз:

  1. Заголовок «Благонадёжность (0–100)» — мелкий текст по центру над диаграммой (i18n-ключ `scoreGauge.title`).
  2. Полукруглая шкала (дуга на 180°):
     - тонкая цветная подложка вдоль всей дуги, разделённая на 3 зоны: розовая/красная слева (низкие), жёлтая/оранжевая посередине (средние), зелёная справа (высокие);
     - поверх подложки — толстая синяя дуга-заливка, показывающая прогресс от начала шкалы до текущего значения (при значении 100 заливка покрывает всю дугу);
     - риски и подписи делений шкалы в точках 0 (крайняя левая), 20, 40, 60, 80, 100 (крайняя правая);
     - красная вертикальная риска-маркер на дуге — точная позиция текущего значения (отдельный элемент, не край синей заливки).
  3. Крупное числовое значение по центру под дугой, цвет по диапазону: низкая 0–39 / средняя 40–69 / высокая 70–100 (симметрично цветовым зонам подложки).
  4. Маленькая точка-индикатор под числом, цвет совпадает с цветом числа.

  Технически: чистый SVG, без сторонних графических библиотек и новых зависимостей. `value = null` — состояние «оценки нет» (без заливки, маркера и точки, вместо числа «—»), необходимо карточке APP-005 до расчёта оценки.

## Этап 2. Аутентификация

- [ ] **AUTH-001** — Регистрация (backend)

  Эндпоинт регистрации: принимает ФИО, дату рождения, логин, пароль, номер телефона, телеграм. Валидация пароля (8–64 символа, латинские строчные и заглавные буквы, цифры, спецсимволы) и формата остальных полей — без подтверждения номера и телеграма.

- [ ] **AUTH-002** — Вход пользователя (backend)

  Эндпоинт входа по логину/паролю, выдача JWT в httpOnly cookie без refresh-токена (TTL — сутки).

- [ ] **AUTH-003** — Вход для сотрудников (backend)

  Отдельный эндпоинт входа по коду с телефона (дефолтный код "123456"). Если в БД нет ни одного пользователя — первый зарегистрированный автоматически становится сотрудником.

- [ ] **AUTH-004** — Страница регистрации (frontend `/registration/`)

  Поля: ФИО, дата рождения, логин, пароль (с подсказкой требований к сложности), повторите пароль, номер телефона, телеграм. Отправка на AUTH-001.

  > Без подтверждения номера и телеграма — только валидация формата, осознанное решение для MVP.

- [ ] **AUTH-005** — Страница входа (frontend `/login/`)

  Поля: логин, пароль. Ссылки "Забыли пароль?" и "Нет аккаунта? Регистрация". Отправка на AUTH-002.

- [ ] **AUTH-006** — Страница входа для сотрудников (frontend `/loginWork/`)

  Поля: логин, код с телефона, пароль. Ссылки "Отправить код" и "Забыли пароль?". Отправка на AUTH-003.

- [ ] **AUTH-007** — Защита приватных маршрутов

  Middleware на бэкенде (проверка JWT из cookie) и route guard на фронтенде: неавторизованный не должен попадать на `/user/*` и `/employee/*`.

- [ ] **AUTH-008** — Иллюстрация рядом с формой на страницах входа/регистрации/входа для персонала

  На `/login/`, `/registration/`, `/loginWork/` рядом с карточкой формы (справа) добавляется фото — по одному на страницу, файлы уже лежат в `public/img/` (найди в проекте актуальные имена файлов, не изобретай их). Отступ между карточкой формы и фото — 4rem. Скругление углов фото — то же значение, что и у карточки формы. Высота фото равна высоте карточки формы и подстраивается под неё динамически (карточка меняет высоту при появлении подсказок/ошибок валидации — фото должно следовать за этим изменением). Ширина фото фиксируется один раз при начальной отрисовке страницы и в дальнейшем не меняется при изменении высоты (используй `object-fit: cover`, чтобы фото кадрировалось по высоте, а не растягивалось/сжималось по ширине).

  Реализуй под единым переключателем (например, один булевый флаг в constants.ts/config, читаемый на всех трёх страницах) — включение/выключение фото на всех трёх страницах разом должно делаться одним изменением этого флага, без правок в каждом компоненте по отдельности.

  > Личная инициатива, не часть исходного кейса — эстетическое решение, при необходимости легко отключается флагом.

## Этап 3. Заявка и скоринг по выписке

- [ ] **APP-001** — Форма новой заявки (frontend `/user/new`)

  Поля: сумма (валидация: от 1 000 до 10 000 000, ошибка "Укажите сумму больше нуля" при пустом/некорректном значении), цель/причина кредита (свободный текст, textarea), телеграм (@username), актуальный телеграм-канал (@channel — обязательное поле, без него форма не отправляется), выписка из банка (загрузка файла), чекбокс согласия с политикой конфиденциальности. В одной строке с кнопкой "Запросить" — поле пароля (доп. верификация личности перед отправкой заявки). Кнопка "Запросить".

  Плейсхолдер поля "Причина" — один из 7 заранее заданных вариантов цели кредита, выбирается случайно при каждой загрузке страницы:
  - На корм для уток
  - На путешествие в Дубай
  - На курс по успешному успеху
  - На новую версию себя
  - На курсы актёрского мастерства
  - На абонемент в спортзал
  - На книгу по саморазвитию

- [ ] **APP-002** — Эндпоинт создания заявки (backend)

  Приём данных формы и файла выписки, создание записи Application со статусом "в обработке".

- [ ] **STMT-001** — Парсинг банковской выписки

  При загрузке файл сразу парсится в структурированные данные (остаток, поступления, траты по категориям за 3 месяца). Сам файл не сохраняется — хранятся только структурированные данные.

- [ ] **STMT-002** — Расчёт скоринга по выписке

  Расчёт вклада в итоговую оценку на основе среднего остатка, регулярности поступлений, доли трат на необходимые товары. Формирует часть позитивных сигналов / факторов риска в ScoreResult.

- [ ] **APP-003** — Пороговая автообработка заявки

  После расчёта итоговой оценки сравнение с порогами из настроек сотрудника (EMP-002): если оценка ≤ порога авто-отклонения — статус "авто-отказано"; если оценка ≥ порога авто-одобрения — статус "авто-одобрено"; иначе заявка уходит в очередь сотрудника.

- [ ] **APP-004** — Список заявок пользователя (frontend `/user/my`)

  Таблица заявок пользователя: id, статус, сумма, дата создания заявки, итоговая оценка. Сортировка по дате создания (по умолчанию — сначала новые).

- [x] **APP-005** — Детальная карточка заявки пользователя (frontend `/user/my?menu={id}`)

  Отображение: id заявки, ФИО заёмщика, запрошенная сумма, цель кредита, итоговая оценка — спидометр "Благонадёжность (0–100)". Это ВСЁ, что видит заёмщик — без разбора сигналов, психологического портрета и отчёта для комитета (это только для сотрудника, см. EMP-005).

  > Временные заглушки: пока реальный API карточки не подключён (см. APP-007), ФИО/цель/оценка заполняются явными константами `FIO_STUB`/`PURPOSE_STUB`/`SCORE_STUB` в `UserMy.jsx` — карточка не показывает пустых/сломанных полей.

- [ ] **APP-007** — Подключение карточки заявки к реальному API

  Передача `full_name` и цели кредита в модалку из `GET /user/applications/{application_id}` (эндпоинт готов), backend-эндпоинт списка заявок `GET /user/applications` для таблицы /user/my, замена моков и заглушек `FIO_STUB`/`PURPOSE_STUB`/`SCORE_STUB` в `UserMy.jsx` на реальные данные.

- [ ] **APP-006** — Настройки профиля пользователя (frontend `/user/settings` + backend)

  Редактируемые поля: ФИО, логин, телеграм, номер телефона, пароль (со сменой).

## Этап 4. Кабинет сотрудника

- [ ] **EMP-001** — Настройки профиля сотрудника (frontend `/employee/settings` + backend)

  Аналогично APP-006: ФИО, логин, телеграм, номер телефона, пароль.

- [ ] **EMP-002** — Настройка порогов автоматизации

  Часть `/employee/settings`, блок "Автоматизация": порог "авто-отклонение ≤ X" и порог "авто-одобрение ≥ Y". Backend хранит оба порога в БД (не хардкод), их использует APP-003.

- [ ] **EMP-003** — Список актуальных заявок (frontend `/employee/newApplication`)

  Таблица заявок, ожидающих решения сотрудника (не попавших под автообработку): id, статус, ФИО заёмщика, сумма, итоговая оценка.

- [ ] **EMP-004** — Список всех заявок (frontend `/employee/application`)

  Таблица всех заявок вне зависимости от статуса: id, статус, ФИО, сумма, итоговая оценка.

- [ ] **EMP-005** — Детальная карточка заявки сотрудника (frontend `/employee/application?menu={id}`)

  То же, что видит заёмщик в APP-005 (id, ФИО, сумма, цель, спидометр), ПЛЮС полный разбор, недоступный заёмщику: блок "Рекомендации системы" (позитивные сигналы и факторы риска двумя списками), блок "Психологический портрет заёмщика" (три метрики по шкале 0–10 — стабильность работы, финансовая грамотность, ответственность), блок "Отчёт для кредитного комитета" (кнопка скачивания + дата последнего обновления), кнопки "Одобрить" и "Отклонить".

- [ ] **EMP-006** — Эндпоинт решения по заявке (backend)

  Приём решения сотрудника (одобрить/отклонить), обновление статуса заявки — изменение сразу отражается в `/user/my` у заёмщика.

## Этап 5. Telegram-скоринг

- [ ] **TG-001** — Парсинг публичного Telegram-канала

  Получение сообщений канала через Telegram Bot API по адресу, указанному в заявке.
  > Если канал недоступен или закрыт — просто не учитывается в оценке, без отдельной обработки ошибки для пользователя.

- [ ] **TG-002** — Расчёт скоринга и психологического портрета по данным канала

  На старте — захардкоженный сценарий (заранее заданные позитивные сигналы, факторы риска, метрики портрета и текст отчёта для демо). Если будет время — реальный анализ лексики, частоты упоминаний работы, подписок на финансовые каналы (LLM+NER).

- [ ] **TG-003** — Интеграция telegram-сигнала в итоговую оценку

  Объединение сигнала из TG-002 с оценкой по выписке (STMT-002) в единый итоговый балл. Должно работать и в отсутствие telegram-сигнала (см. TG-001) — тогда используется только оценка по выписке.
